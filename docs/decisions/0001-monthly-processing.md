# ADR-0001：月次処理の実行基盤

- **状態**：暫定（技術検証の前）
- **日付**：2026-11-03

## Context（背景）

新しい業務アプリは、業務時間中ずっとオンライン業務で使われます。ここに、月末に多数の対象をまとめて点検し、帳票を作る月次処理を追加します。月次処理は、想定する最大件数を4時間以内に処理し、その間もオンライン業務の応答を遅らせてはいけません。一部が失敗したときは、その部分だけを重複なく再実行できる必要があります。

## Options considered（比較した選択肢）

1. 標準の AWS Lambda（処理を15分以内の単位に分けて動かす）
2. Amazon ECS のタスク（AWS Fargate で1つまたは少数の長い処理として動かす）
3. AWS Batch（AWS Fargate で、ジョブのキューと再実行の仕組みを使って動かす）

## Verified facts and sources（確認した事実と出典）

確認日：2026-11-03（aws-mcp で確認）

- 標準の AWS Lambda 関数のタイムアウトは最大900秒（15分）。
  https://docs.aws.amazon.com/lambda/latest/dg/configuration-timeout.html
- AWS Batch は、失敗したジョブを自動で再実行する設定を持つ。試行回数は1～10回で指定できる。
  https://docs.aws.amazon.com/batch/latest/userguide/job_retries.html
- Amazon ECS のサービスに属さない単独のタスクは、止まってもサービスのスケジューラーによる置き換えの対象にならない。再実行と進み具合の管理は別に用意する必要がある。
  https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-maintenance.html
- 東京リージョン（ap-northeast-1）では、AWS Lambda、Amazon ECS、AWS Fargate、AWS Batch が使える（aws-mcp の `get_regional_availability` で確認）。

## Project-specific inference（このプロジェクトへの推論）

- 4時間以内に多数の対象を処理し、失敗した部分を再実行する必要があるため、ジョブのキューと再実行の仕組みを持つ AWS Batch が最初の候補として扱いやすい。
- 標準の Lambda を使うなら、1回の処理を15分より十分短く分け、重複や途中の失敗に備えた作りが前提になる。
- 実行基盤をオンライン業務と分けても、同じデータベースを使うなら、接続数や負荷の取り合いでオンライン業務が遅くなるおそれがある。

## Decision（判断）

月次処理は、次に AWS Batch（AWS Fargate で実行）で技術検証する。これは最終決定ではない。

## Unknowns and validation（未確認の事項と技術検証）

未確認の事項：

- 月次処理の最大件数と、その増え方
- 1件あたり、1まとまり（チャンク）あたりの処理時間
- データベースに許される接続数と負荷の上限
- 4時間の期限の始まりと終わりの定義

技術検証：

1. 最大件数の合成データを作り、一定の件数ずつのチャンクに分ける。
2. AWS Batch で同時に動かす数を変えながら実行する。
3. 全体の時間、チャンクごとの時間、再実行の回数、データベースの接続数と負荷、オンライン API の応答時間を測る。
4. 合格の基準：全体が4時間以内に終わり、オンライン API の応答時間とデータベースの負荷が上限の内に収まる。

## Revisit conditions（見直す条件）

- どのチャンクも15分より十分短く終わり、重複と途中の失敗を扱えるなら、標準の Lambda を比べ直す。
- 処理が1つか少数の長い処理で、再実行と進み具合を管理する仕組みがすでにあるなら、Amazon ECS のタスクを比べ直す。
- データベースへの負荷がオンライン業務を遅らせるなら、月末時点のデータの写しを使う方法を検討する。
